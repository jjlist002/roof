## 3. Web3Forms access key 보안에 대한 정리

> 사용자 질문: "엑세스 키를 .dev.vars 에 입력하지 않고 깃허브에 올린거야? 민감한 정보를?"

### 결론: 이 키는 공개되어도 괜찮음 (의도된 공개 키)

이유:
1. 이 사이트는 **정적(static) 사이트**이고 폼 전송이 사용자의 브라우저에서 직접 Web3Forms API로 호출됨
2. 따라서 누구든 브라우저 개발자도구에서 `main.js` 를 열면 그대로 보임 — **숨길 수 없는 구조**
3. Web3Forms 공식 문서도 이를 "public access key" 라고 명시
4. 같은 패턴이 Formspree, EmailJS, Getform 등 모든 클라이언트사이드 폼 서비스에 동일

### `.dev.vars` 가 답이 아닌 이유
- `.dev.vars` 는 **서버사이드** 시크릿용 (Cloudflare Workers/Pages 등)
- 이 사이트는 서버가 없는 정적 사이트라 빌드 시 어차피 JS에 박혀 클라이언트에 노출됨
- 진짜로 숨기려면 별도 백엔드 프록시를 만들어야 하는데, 이 규모에 과도함

### 진짜 보호는 어디서 하나
키를 숨기는 대신 **Web3Forms 대시보드의 도메인 화이트리스트 + hCaptcha 로 악용을 차단**하는 것이 정석. (위 2번 항목 참고)

비교: AWS 시크릿 키, DB 비밀번호 같은 것은 절대 클라이언트로 가면 안 되는 진짜 시크릿. Web3Forms access key 는 성격이 전혀 다름.

## 4. GitHub push 자동 인증 메커니즘

> 사용자 질문: "이번에 인증했으니까 추후엔 자동 push 되는지?"

### 현재 인증 구조
- 일반적인 `credential.helper` (예: store, cache, libsecret) **사용 안 함**
- `~/.git-credentials` 파일도 **없음**
- 대신 환경변수가 핵심:
  ```
  GIT_ASKPASS=/nix/store/.../code-oss/extensions/git/dist/askpass.sh
  VSCODE_GIT_IPC_HANDLE=/tmp/vscode-git-3ec96f3c10.sock
  ```
- 즉, **Firebase Studio(=VS Code 기반) 의 GitHub 인증 통합**을 사용 중
- 자격증명은 파일이 아니라 VS Code 의 시크릿 스토리지(메모리/keychain)에 보관됨
- `git push` → askpass 스크립트 → IPC 소켓으로 에디터에 질의 → 저장된 GitHub 세션 토큰 반환 → push 성공

### 앞으로 인증창이 뜨는가

| 상황 | 인증창 |
|------|--------|
| 같은 세션에서 또 push | ❌ 안 뜸 |
| Firebase Studio 재시작 후 push | ❌ 보통 안 뜸 |
| 토큰 만료 시 (수 주~수 개월에 한 번) | ✅ 한 번 뜸, 그 후 다시 자동 |
| GitHub 비밀번호 변경/토큰 폐기 후 | ✅ 다시 뜸 |
| VS Code 에서 GitHub 로그아웃 후 | ✅ 다시 뜸 |

### 결론
**일반적으로 자동화 상태이며, 가끔(드물게) 토큰 만료 시에만 한 번 인증창이 뜸. 한 번 클릭하면 다시 자동화.**

이전에 사용자가 "인증창이 떠서 취소했다"고 한 것은 만료 갱신 요청이었을 가능성이 높음. 그 후 어느 시점에 자동 갱신이 되었거나 캐시 토큰이 살아있어서 이번 push 는 추가 인증 없이 성공함.
